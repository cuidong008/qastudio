# 分析题：多章合并上下文生成方案

## 一、目标与原则

- **分析题**生成时：
  - **多章**：将**所有选中章节的内容合并**成一份上下文，一次性送给大模型生成分析题（不逐章生成）。
  - **单章**：将该章**全部内容**送入（与现有单章逻辑一致，无需改）。
- **其他题型**（单选、多选、判断、填空、问答）：保持现有「逐章生成」策略不变。

---

## 二、整体流程

### 2.1 多章 + 分析题

```
用户选择：课程 + 多章 + 各题型数量（含 analysis_max > 0）
                    │
                    ├── 分析题：调用「多章合并上下文」接口 1 次
                    │   - 入参：chapter_ids, analysis_max, ...
                    │   - 后端：合并所有 chapter 的文档+知识点 → 一份 context → 生成 analysis_max 道分析题
                    │   - 每道题归属章节：按 chapter_ids 轮询分配（round-robin），便于入库
                    │
                    └── 其余题型：仍按章循环，每章调用现有单章生成（且该次请求中 analysis_max=0）
                        - 每章只生成 single_choice / multiple_choice / judge / qa / blank
```

### 2.2 单章

- 不区分题型，**仍用现有单章接口**：该章文档+知识点一份 context，按题型分批生成（含分析题）。  
- 单章时「把单章内容都送入」已满足，无需新增接口。

---

## 三、后端修改

### 3.1 新增：多章合并上下文仅生成分析题

**用途**：仅在「多章 + 需要生成分析题」时使用；单章或不需要分析题时不调用。

| 项目 | 说明 |
|------|------|
| **接口 1（预览）** | `POST /teacher/courses/{course_id}/questions/generate-analysis-preview` |
| **请求体** | `chapter_ids: list[int]`（至少 2 个）、`analysis_max: int`、`analysis_difficulty_score: float`、`question_bank_type: str`；可选 `knowledge_point_ids: list[int]`（若传则只取这些知识点所在章的内容中对应知识点片段，复杂时可先不按 KP 过滤，整章合并）。 |
| **逻辑** | 1）校验 course 归属、chapter_ids 均属于该 course。<br>2）按 chapter 顺序逐个拉取：该章 KnowledgeDocument（如最多 30 条）+ 该章知识点（若未传 knowledge_point_ids 则用该章全部知识点；若无则可为该章自动生成若干条）。<br>3）合并为一份 context：每章一段，带明显标题如「章节：{章节标题}」，段内为「文档：…」「知识点：…」。总长截断（建议 40000～50000 字符，可配置）。<br>4）仅生成 analysis 题型：调用现有分析题 prompt（或与问答题类似的 prompt，类型为 analysis），生成 analysis_max 道；若超出单次 output 预算则按批生成。<br>5）返回预览列表；每条带 `chapter_id`：按 chapter_ids 轮询分配（第 1 题→chapter_ids[0]，第 2 题→chapter_ids[1]，…），便于前端展示和后续导入。 |
| **响应** | 与现有 generate-preview 的题目列表结构一致（含 chapter_id、question_text、correct_answer、explanation、difficulty_score 等），便于前端与 per-chapter 预览合并。 |

| 项目 | 说明 |
|------|------|
| **接口 2（正式生成并入库）** | 方案 A：`POST /teacher/courses/{course_id}/questions/generate-analysis`，请求体同上，生成后直接入库，每题 chapter_id 轮询。<br>方案 B：不单独接口，而是通过「生成任务」触发（见下）。 |

### 3.2 合并上下文的实现要点

- **函数**：如 `_build_merged_context_for_chapters(db, course_id, chapter_ids, knowledge_point_ids=None)`。
  - 顺序遍历每个 chapter_id，拉取该章文档 + 该章知识点（或按 knowledge_point_ids 过滤该章内知识点）。
  - 每章一段：`\n\n## 章节：{chapter.title}\n\n` + 文档块 + 知识点块。
  - 拼接后总长度截断（例如 45000 字符），返回 `(merged_context, list[(chapter_id, chapter_title)])` 供 prompt 使用。
- **Prompt**：明确说明「以下为多章合并内容，请根据整体内容出分析题，题干与答案需分点、符合工程教育认证」；题型仅 analysis，数量为 analysis_max。

### 3.3 正式生成任务（多章 + 分析题）

- **任务模型**：沿用现有 `QuestionGenerationTask`。多章分析题任务可：
  - 取 `chapter_id = chapter_ids[0]`（满足非空 FK），在 `request_payload` 中存 `analysis_only: true`、`chapter_ids: [1,2,3]`、`analysis_max`、难度等。
- **执行逻辑**（如 `_run_question_generation_task` 或单独 runner）：
  - 若 `request_payload.analysis_only === true`：只做「合并 context + 仅生成 analysis」，不按章循环；生成后逐题入库，chapter_id 按 chapter_ids 轮询。
  - 否则保持现有「单章生成」逻辑。
- **前端**：多章且 analysis_max > 0 时，除为每章创建原有单章任务（且每章请求里 analysis_max 置 0）外，再创建**一条**「分析题专用任务」（带 chapter_ids、analysis_only、analysis_max）。查询任务列表时能看到这条任务；结果中 by_type 仅有 analysis。

### 3.4 单章逻辑

- 单章时**不**调用上述多章分析题接口；现有 `_generate_questions_for_chapter` 已对该章用「该章全部文档+知识点」生成所有题型（含分析题）。  
- 只需在现有 prompt/题型分支中支持 `analysis` 类型即可（与「分析题」题型方案一致）。

---

## 四、前端修改

### 4.1 预览（生成习题预览）

- **多章 + analysis_max > 0**：
  1. 先请求一次 **generate-analysis-preview**：`course_id`、`chapter_ids: targetChapterIds`、`analysis_max`、难度等；得到分析题预览列表（每条带 chapter_id）。
  2. 再对**每一章**请求现有 **generateChapterQuestionsPreview**，请求体中：  
     - `analysis_max: 0`（该章不再生成分析题），  
     - 其余题型数量仍为按章均分后的值（single_choice_max, multiple_choice_max, …）。
  3. 将 1 的列表与 2 的各章列表**合并**为同一预览表格，展示、编辑、导入逻辑不变；导入时每条已有 chapter_id。
- **单章**：不调用 generate-analysis-preview；只调现有单章预览（含 analysis_max），无需改动。

### 4.2 正式生成（提交后台任务）

- **多章 + analysis_max > 0**：
  - 为每章创建**原有**生成任务（请求体里该章分配到的题型数量，且 **analysis_max: 0**）。
  - 额外创建 **1 条**「分析题多章」任务：传入 course_id、chapter_ids、analysis_max、难度等（后端用 request_payload 的 analysis_only + chapter_ids 识别）。
- **单章**：只创建一条现有单章任务（含 analysis_max），无需新逻辑。

### 4.3 API 与类型

- 新增：`generateAnalysisPreview(courseId, body)`、`generateAnalysis(courseId, body)`（若采用单独接口入库），或仅预览接口 + 任务方式入库。
- 请求体类型：`chapter_ids: number[]`、`analysis_max: number`、`analysis_difficulty_score?: number`、`question_bank_type?: string` 等。

---

## 五、数据与配置

- 分析题题型已在「分析题题型方案」中纳入（question_type=analysis、prompt、难度等）。
- 多章合并时 context 长度上限建议单独配置（如 `analysis_merged_context_max_chars = 45000`），避免单次输入过长。

## 六、修改清单汇总

| 层级 | 文件/模块 | 改动要点 |
|------|------------|----------|
| 后端 | teacher 路由 | 新增 `POST .../courses/{course_id}/questions/generate-analysis-preview`；可选 `POST .../generate-analysis` 或仅通过任务入库。 |
| 后端 | teacher 逻辑 | `_build_merged_context_for_chapters`；分析题专用 prompt（多章合并说明）；生成结果带 chapter_id 轮询。 |
| 后端 | 任务执行 | 识别 `request_payload.analysis_only` + `chapter_ids`，执行合并上下文仅生成 analysis 并入库（chapter_id 轮询）。 |
| 后端 | 配置 | 可选：`analysis_merged_context_max_chars`。 |
| 前端 | TeacherQuestionBank 预览 | 多章且 analysis_max>0 时先调 generate-analysis-preview，再 per-chapter 调 generate-preview（analysis_max=0），合并列表。 |
| 前端 | TeacherQuestionBank 正式生成 | 多章且 analysis_max>0 时，除每章任务外再创建一条分析题多章任务。 |
| 前端 | api/client | 新增 generateAnalysisPreview（及可选 generateAnalysis）。 |

## 七、单章 vs 多章小结

| 场景 | 分析题内容来源 | 接口/任务 |
|------|----------------|-----------|
| 单章 | 该章全部文档+知识点（一份） | 现有单章 generate/preview，一次请求，含 analysis_max。 |
| 多章 | 所有选中章的文档+知识点合并（一份） | 新增「分析题多章」预览 + 任务；其余题型仍按章逐次生成（每章 analysis_max=0）。 |

这样实现后：**分析题在多章时是多章内容一起送大模型生成，单章时是该章全部内容送入**，与现有其余题型「逐章生成」策略分离，互不影响。
